# 05 · 用接口文档跑通全链路（不用装 App）

## 这份文档解决什么问题

装 Android 环境要下好几个 G，还得配 SDK、连真机。但**后端对不对，其实不用等 App**——
FastAPI 自带一个网页版调试界面，浏览器打开就能把「拍照识别 → 确认入库 → 生成菜谱 → 算采购清单」
整条链路亲手点一遍。五分钟，零安装。

**什么时候用**：刚跑起后端、想确认它真的活着；或者 App 那边报错、要判断是前端问题还是后端问题。

---

## 一、先确认服务在跑

1. 双击项目根目录的 `start-backend.bat`，等窗口里出现 `Uvicorn running on http://0.0.0.0:8000`
2. 浏览器地址栏输入下面这一行（**整行复制，结尾不能有任何多余字符**）：

```
http://127.0.0.1:8000/docs
```

3. 应该看到标题写着「冰箱先知 Fridge Prophet API」

> ⚠️ **地址栏里必须干干净净地只有 `http://127.0.0.1:8000/docs`。**
> 如果末尾多带了 `**`、`。`、空格之类的字符（比如从加粗的文档里复制时会带上星号），
> 浏览器会去请求一个不存在的路径，页面显示 `{"detail":"Not Found"}` —— 那不是后端坏了，
> 把地址栏里多余的部分删掉再回车就好。

> **这个窗口不要关。** 关了服务就停了，网页会变成「无法访问」。
> 想停服务就在那个黑窗口里按 `Ctrl + C`。

---

## 二、页面长什么样

打开后从上往下依次是：

| 位置 | 内容 | 说明 |
|---|---|---|
| 顶部 | 「冰箱先知 Fridge Prophet API」+ `0.1.0` | 版本号来自 `app/main.py` 的 `FastAPI(...)` 配置 |
| 右上 | **Authorize** 按钮 | 粘登录令牌用，不点它调业务接口全是 401 |
| 下方 | `Filter by tag` 筛选框 | 34 个接口一屏看不完，输入关键词过滤 |
| 主体 | 7 组接口 | 鉴权(3)、用户画像(7)、冰箱库存(8)、AI 识别(2)、AI 菜谱(6)、智能采购(6)、系统(2) |

每个接口左边有个**蓝色 `GET` / 绿色 `POST`** 标签，表示 HTTP 方法：

- `GET` = 只读，查数据用
- `POST` = 会写数据，或者要传一大坨内容
- `PATCH` / `PUT` / `DELETE` = 改、删

**点一下整行标题，它才会展开。** 展开后右边才出现 `Try it out` 按钮——
不展开是找不到按钮的，这是新手最常卡住的地方。

## 三、七步跑完整条链路

按顺序来，每一步都依赖上一步的返回值。

### 第 1 步：注册账号，拿令牌

展开 `POST /api/v1/auth/register` → 点 **Try it out** → 请求体改成：

```json
{
  "email": "test@example.com",
  "password": "123456",
  "nickname": "测试"
}
```

→ 点 **Execute**。

⚠️ 注意字段是 **`email` 不是 `username`**。填成 `username` 会报 `422 Unprocessable Entity`，
展开 `Response body` 里的 `detail` 会明确告诉你是哪个字段缺了。

返回长这样：

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "bearer",
  "expires_in": 604800,
  "user": { "id": 1, "email": "test@example.com", ... }
}
```

把 `access_token` 后面那串**整个复制下来**（很长，别只复制一半）。
`expires_in: 604800` 是 7 天有效期，够用了。

### 第 2 步：让页面记住令牌

点右上角 **Authorize** → 把令牌粘进输入框 → 点 **Authorize** → 再点 **Close**。

⚠️ **前面不要自己加 `Bearer ` 两个字**。接口用的是 HTTP Bearer 认证，
程序会自动在请求头里拼上 `Authorization: Bearer <你的令牌>`，你手动加会变成 `Bearer Bearer xxx`，
反而认证失败。

做完这步，接口行左边的锁图标会变成「已解锁」的样子。

### 第 3 步：先看 AI 处于哪种模式

展开 `GET /api/v1/vision/status` → Execute。

这个接口在页面上**不会显示示例返回**（因为它返回的是自由格式字典，Swagger 没法预先画出来），
点了 Execute 才有真实内容。没配密钥时看到的就是这样：

```json
{
  "ai_enabled": false,
  "vision_model": "mock",
  "text_model": "mock",
  "storage": "local",
  "note": "未配置 DASHSCOPE_API_KEY，当前返回演示数据"
}
```

五个字段的含义：

| 字段 | 值 | 含义 |
|---|---|---|
| `ai_enabled` | `false` | **判断 AI 有没有接上的唯一依据**。`false` = 走 MOCK 模式 |
| `vision_model` | `mock` | 视觉识别用的模型。没配密钥时固定显示 `mock` |
| `text_model` | `mock` | 文本生成用的模型。没配密钥时固定显示 `mock` |
| `storage` | `local` | 照片存哪儿。`local` = 本机磁盘；配了 Supabase 会变 `supabase` |
| `note` | — | 人话说明，直接告诉你是哪种状态 |

配上 `DASHSCOPE_API_KEY` 后，会变成：

```json
{
  "ai_enabled": true,
  "vision_model": "qwen-vl-max",
  "text_model": "qwen-plus",
  "storage": "local",
  "note": "已接入通义千问"
}
```

**`ai_enabled: false` 是正常的，不要当成错误。** 这时走的是内置假数据，
整条链路照样跑通 —— 比赛现场断网就靠它保命。先让 MOCK 跑通，
等以后换上真密钥，如果出问题你就能确定是 AI 的问题，而不是链路的问题。

### 第 4 步：传一张冰箱照片上去识别

展开 `POST /api/v1/vision/scan` → Try it out → 点 **Choose File** 选一张冰箱内部的照片
→ Execute。

返回体里的 `foods` 数组就是 AI 认出来的食材。

**MOCK 模式下返回的是写死的 5 条演示数据**，不管你传什么照片都是这 5 条：

```json
{
  "scan_id": "a1b2c3d4e5f60718",
  "foods": [
    { "name": "鸡蛋",   "quantity": 6,   "unit": "个", "confidence": 0.96, "category": "蛋类",   "storage_location": "冷藏", "shelf_life_days": 30 },
    { "name": "西红柿", "quantity": 3,   "unit": "个", "confidence": 0.91, "category": "蔬菜",   "storage_location": "冷藏", "shelf_life_days": 7 },
    { "name": "豆腐",   "quantity": 1,   "unit": "盒", "confidence": 0.88, "category": "豆制品", "storage_location": "冷藏", "shelf_life_days": 3 },
    { "name": "鸡胸肉", "quantity": 450, "unit": "g",  "confidence": 0.84, "category": "肉类",   "storage_location": "冷冻", "shelf_life_days": 30 },
    { "name": "牛奶",   "quantity": 1,   "unit": "盒", "confidence": 0.93, "category": "乳制品", "storage_location": "冷藏", "shelf_life_days": 7 }
  ],
  "image_url": "/uploads/1/a1b2c3d4e5f60718.png",
  "needs_review": true,
  "model": "mock",
  "message": "当前为演示数据（未配置 AI 密钥）。配置 DASHSCOPE_API_KEY 后将使用 qwen-vl-max 真实识别。"
}
```

看到 `"model": "mock"` 和 message 里那句「当前为演示数据」就说明走的是 MOCK，
**这是正常的**，不是识别失败。上面这 5 条数据在 `app/services/vision_service.py`
的 `MOCK_FOODS` 里写死，就是为了让你在没配密钥时也能把后面的步骤走完。

配了真密钥之后，`model` 会变成 `qwen-vl-max`，`foods` 变成照片里真实的东西。

**这一步只返回候选，没有写进数据库。** 这是我们刻意设计的——
策划书里强调的「用户确认机制」，AI 认错了不能直接污染库存。

照片建议：冰箱里东西多一点、光线亮一点。只支持 JPG / PNG / WEBP，
传别的格式（比如 .txt、.heic 之外的）会返回 `415`。

### 第 5 步：确认，真正写进冰箱

展开 `POST /api/v1/inventory/confirm` → Try it out → 把上一步返回的 **`foods` 数组整个**
复制进请求体的 `foods` 字段：

```json
{
  "foods": [
    { "name": "鸡蛋", "quantity": 6, "unit": "个",
      "category": "蛋类", "storage_location": "冷藏", "shelf_life_days": 30 }
  ],
  "default_storage_location": "冷藏"
}
```

→ Execute。**返回 `201` 才算写进去了**（201 = 新建成功，200 是查询成功，别搞混）。

> 同名食材会自动累加数量，不会出现两条「鸡蛋」。

### 第 6 步：验证食材真的在库里

展开 `GET /api/v1/inventory` → Execute。

应该看到刚确认的食材，每条带 `days_left`（还有几天过期）和 `freshness`（新鲜度）。
这两个字段是 App 首页顶部那几个数字的来源。

顺便可以试 `GET /api/v1/inventory/stats`，看库存概览的汇总数字。

### 第 7 步：生成菜谱，再算采购清单

先展开 `POST /api/v1/recipes/generate` → Execute（请求体默认就行，`count: 3` 表示生成 3 个）
→ 在返回的 `recipes` 数组里记下第一个的 `id` 数字。

再展开 `POST /api/v1/shopping/build` → 请求体填：

```json
{ "recipe_ids": [1] }
```

→ Execute。返回的 `items` 就是你要去买的东西：

```json
{
  "id": 1,
  "title": "采购清单",
  "items": [
    { "food_name": "嫩豆腐", "quantity": 300, "unit": "g",
      "estimated_price": 3.5, "checked": false, "applied_to_inventory": false }
  ],
  "estimated_total": 3.5
}
```

---

## 四、最后一步：买完写回冰箱

展开 `POST /api/v1/shopping/{list_id}/apply` → 把 `list_id` 填成上一步返回的 `id`（比如 `1`）
→ Execute。

这会把清单里**已勾选**的商品写回冰箱库存，`applied_to_inventory` 变成 `true`。
再去 `GET /api/v1/inventory` 看，买的东西应该出现在里面了。

**这就是闭环**：识别 → 管理 → 推荐 → 烹饪 → 采购 → 再识别。

## 五、跑不通时的对照表

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 网页打不开、转圈 | 服务没在跑，或那个黑窗口被关了 | 重新双击 `start-backend.bat` |
| 页面显示 `{"detail":"Not Found"}` | 地址栏里的网址多了字符（常见是从加粗文本里复制带上了 `**`） | 地址栏改成干净的 `http://127.0.0.1:8000/docs` 再回车。**这不是后端坏了** |
| 页面白屏，什么都不显示 | 这个页面要从 `cdn.jsdelivr.net` 下载样式，**断网就白屏** | 连上网刷新；或直接访问 `http://127.0.0.1:8000/redoc` 试试 |
| 所有接口都返回 `401 Not authenticated` | 没点 Authorize，或令牌过期了（7 天） | 重新走第 1、2 步 |
| `422 Unprocessable Entity` | 请求体字段名或类型不对 | 展开 `Response body` 的 `detail`，它逐字告诉你哪个字段错了 |
| 第 5 步返回 `422` 说 `foods` 缺失 | 数组没粘全，或者 JSON 被截断了 | 回到第 4 步重新整段复制 `foods` 的值 |
| 照片传上去识别结果为空 | 照片太暗/太糊/冰箱太空 | 换一张光线好、东西多的 |
| 改了代码但行为没变 | 8000 端口上可能有**两个进程**（旧的绑 127.0.0.1，新的绑 0.0.0.0） | `netstat -ano \| grep ":8000.*LISTENING"`，把多余的 PID 用 `Stop-Process -Id <PID> -Force` 杀掉 |

> **关于「改了代码没生效」这个坑**：Windows 上 `127.0.0.1:8000` 和 `0.0.0.0:8000` 可以同时存在。
> 而 `curl 127.0.0.1:8000` 会优先命中**更具体的**那个 —— 也就是旧进程。
> 所以重启服务前一定要确认端口上只剩一个进程。

## 六、两条重要提醒

**1. 这个页面只是调试工具，不是给用户用的。**
它没有界面设计、没有登录页，而且**任何能访问到的人都能调你的接口**。
`docs/03-部署到公网.md` 里那条「上线后关掉接口文档」就是为它准备的 ——
正式部署时要在环境变量里设 `ENABLE_DOCS=false`，别把调试入口暴露在公网上。

**2. 第 7 步的结果要交叉验证。**
菜谱详情里的 `missing_ingredients`（缺什么）和采购清单里的 `items`（买什么）**必须对得上**。
如果菜谱页显示「豆腐 ✓ 有」而采购清单却让你去买豆腐，说明 `recipe_service` 和
`shopping_service` 的单位判断规则又跑偏了 —— 这是曾经踩过的真 bug，发现就立刻提出来。
