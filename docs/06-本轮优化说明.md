## 反馈 ①：写回冰箱后，这道菜该像完成的任务一样退到后面

> 原话：「在我按照菜谱进入采购清单之后，选择写回冰箱后这个菜应该像完成了的任务一样消失或者暗色置底，而不是需要我手动删除，而且删除的时候出现了 bug，无法正常删除」

### 1a. 删除功能全线失效（这是个真 bug）

- **现象**：所有「删除」按钮都报
  `Response from FridgeApi.deleteXxx was null but response body type was declared as non-null`
- **原因**：后端 6 个删除接口成功时返回 `204 No Content`，**响应体是空的**；
  客户端却把返回类型声明成非空的 `ResponseBody`，Retrofit 在空响应体上做非空校验，直接抛异常。
- **修法**：5 处改成 `ResponseBody?`（可空）。
- **代码**：`android/.../data/remote/FridgeApi.kt`（文件顶部有注释说明这个坑，新增删除接口照抄）

### 1b. 菜谱列表不再用真实库存算缺料（也是 bug）

- **现象**：菜谱列表里每道菜都显示「食材齐全」，怎么买菜都不变。
- **原因**：`GET /recipes` 直接把 `missing_ingredients` 填成空数组，没有拿当前库存重算。
  于是客户端那句 `if (missingIngredients.isEmpty())` 永远成立，
  「食材齐全」筛选也因此形同虚设。
- **修法**：列表接口和详情接口一样，用当前库存重算缺料；
  并新增 `ready` 字段（配料表非空且一样不缺 = 现在就能做）。
- **代码**：`backend/app/api/v1/recipes.py` 的 `list_recipes` + `_with_availability`

### 1c. 已备齐的菜自动弱化置底

- 列表排序：待采购的在前，`ready` 的沉到最后（稳定排序，同类之间仍是「最新的在前」）。
- 视觉：已备齐的卡片整体透明度降到 0.6，标签从「缺 N 样」变成「已备齐」。
- 分组处插一条说明「以下 N 道食材已备齐」，否则用户会以为界面乱了。
- 筛选新增「待采购」（把已备齐的彻底藏起来）和「现在能做」。
- 采购清单同样处理：`status = done` 的清单沉底、透明度 0.62、明细默认收起。
- **代码**：`RecipesViewModel.visibleRecipes()`、`RecipesScreen.ReadyDivider`、
  `ShoppingScreen.DoneDivider`

> **设计取舍**：用户说「消失**或者**暗色置底」，我们选了「暗色置底」而不是直接隐藏。
> 理由：直接隐藏会让用户以为菜谱被删了；暗色置底既让出了视觉重心，又保留了「我还做过这道菜」的记录。
> 真想让它消失的，用「待采购」筛选即可。

## 反馈 ②：头像、个性简介、健康偏好扩充

### 2a. 头像

- 后端新增 `POST /users/avatar`，走和冰箱照片同一套存储层（Supabase Storage，未配置则落本地磁盘）。
- 文件名用随机串（`avatars/{用户id}/{16位随机}{后缀}`），避免路径穿越、重名覆盖、中文名编码问题。
- 限制：JPG / PNG / WEBP，≤ 5MB。
- 客户端点一下头像就能换：用 `PickVisualMedia`（Android 13+ 官方相册选择器），
  **不需要申请存储权限**，用户选中哪张就只授权哪张。
- 没上传头像时显示昵称首字 + 按昵称哈希出的渐变色，不会出现空白圆圈。

### 2b. 个性简介

- `User` 表加 `bio` 字段（≤ 200 字），走轻量级自动迁移补列，不用重建库。
- 区分两种「空」：传 `null` = 不改动，传 `""` = 清空。客户端清空输入框时传空串，所以能真的清掉。

### 2c. 健康偏好从 6 项扩到 11 项

新增：控糖、补钙、补铁、低嘌呤、不吃生食。

- 每项都带一句人话解释（比如「低嘌呤 —— 痛风 / 高尿酸适用」），
  否则用户看不懂就直接跳过了。
- ⚠️ **踩过的坑**：客户端 `HealthPreferenceOut.toInput()` 用的是「默认参数补齐其余字段」的写法。
  新增字段时如果忘了往这个函数里加，用户每点一个开关就会把新字段**静默重置成 false** ——
  表现是「开了控糖，补钙自己关了」。所以那里留了醒目注释。

### 2d. 忌口 / 过敏库改为后端下发

- 新增 `GET /users/options`，返回分组的过敏原（3 组 20 条）和常见忌口（5 组）。
- 编辑画像时直接渲染成可点选标签，点一下加入输入框（**追加**而不是替换，
  因为用户往往既想点标签又想手写补充）。
- 放后端而不是写死在 App 里：以后往库里加食材改后端就生效，不用发版。

## 反馈 ③：食材支持手选购买日期与保质期

### 手动添加

- 新增「购买日期」（默认今天，可改）和「保质期」快捷选项
  （系统估算 / 3 / 7 / 15 / 30 / 90 天）。
- 选「系统估算」时后端按食材名查内置默认保质期。

### 扫描识别

- 识别结果里每一项都能展开「购买日期 / 保质期」。
- **默认收起**：一次扫描常有十几种食材，全展开页面会长得没法看；
  收起时那一行也会显示已改的日期摘要，用户知道自己动过什么。
- 日期填反（过期早于购买）会在本地就拦住并指出是哪一项，
  不让它跑到后端变成一个看不懂的「数据格式不正确」。

### 编辑已有食材

- 原来的「改数量」对话框升级成「数量 + 购买日期 + 过期日期」。
- 购买日期和过期日期是**两个独立输入**，不是「日期 + 天数」：
  牛奶盒上印着到期日但购买日期是自己记的，两个信息经常只有一个在手。

### 后端规则（优先级从高到低）

1. 用户显式指定的过期日期
2. 购买日期 + 用户给的保质期天数
3. 购买日期 + 按食材名查到的默认保质期
4. 都没给 → 今天 + 默认保质期

另外：同名食材累加库存时，过期日期取**更早**的那个 ——
宁可早提醒，也不能把快过期的东西显示成新鲜的。

## 反馈 ④：食品安全小贴士

### 内容取向：科学辟谣，不是「食物相克大全」

用户举的例子是「螃蟹和西红柿同吃会怎么样」。查下来这条是**谣言**
（要达到中毒剂量得一次吃下几百公斤螃蟹），所以内容库的定位是
**「科学辟谣 + 权威机构确认的真实要点」**。

理由：在一个食品安全类应用里传播伪科学是负价值，答辩时被问到也会很尴尬。

- 18 条贴士，分 4 类：食物相克辟谣 / 储存安全 / 烹饪安全 / 特殊人群
- 结论分 4 档：谣言 / 部分属实 / 属实 / 注意
- 每条含：标题、一句话摘要、原因与原理正文、依据来源（中国营养学会、
  国家食品安全风险评估中心、WHO 等）
- **颜色语义**：「谣言」用**绿色**（意思是「可以放心」）。
  如果给谣言标红，用户会以为「这条很危险」，正好理解反了。

### 位置

- 首页「扫描我的冰箱」主按钮**下方**：不抢唯一核心动作的视觉重心。
  一条标题 + 两行摘要，左侧 3dp 竖色条提示结论，右侧「看原理 ›」。
- 首页还有「全部贴士 ›」入口，以及「我的」页里的入口卡片。
- 详情页版式是「先给结论，再讲道理」：整块彩色横幅放结论，
  想深究的再往下读原理和出处。

### 接口

- `GET /tips`（支持分类 / 结论筛选）、`GET /tips/random`、`GET /tips/{id}`
- **刻意不要求登录**：内容是静态公共知识、不含用户数据，不鉴权还能让登录页也展示一条。
- 客户端有一层内存缓存：断网时首页标语位显示上次的内容，而不是整块消失。

## 反馈 ⑤：菜谱配图

### 为什么不用 AI 现画

1. **慢**：用户点「生成菜谱」要立刻看到结果，画图要几十秒
2. **贵**：每次都要花钱，且同一道菜每次画出来不一样，看着廉价
3. **脆**：断网 / MOCK 模式下彻底没图 —— 而 MOCK 是比赛现场的保命机制

### 做法：项目自带的本地图片库 + 三级匹配

```
第 1 层  菜名 → 具体菜品      「番茄炒蛋」→ tomato-egg
第 2 层  菜名/食材 → 主食材    「蒜蓉西兰花」→ broccoli
第 3 层  兜底                 default
```

- 匹配是**确定性**的：同一道菜永远得到同一张图。
- 逐级退化时只认**磁盘上真实存在**的图，所以现在图片一张没有也能正常跑
  （接口返回 `image_url: null`，App 显示占位图）。
- **加图不用改代码**：把图片命名成 `<key>.jpg` 丢进 `backend/static/recipes/` 即可。

### 没有图时也不会出现空白框

占位图用菜名哈希出一个色相做柔和渐变，中间放菜名首字 ——
不同菜的占位色不一样，看着是「有意设计」而不是「坏了」。

### 客户端怎么加载图片（自研，没引第三方库）

App 端**没有用 Coil / Glide**，而是用项目里已有的 OkHttp + `BitmapFactory`
写了一个约 100 行的加载器（`android/.../ui/components/RemoteImage.kt`）。

原因不是「想省事」，而是 **Coil 3 会让本项目的构建直接失败**：

```
Corrupt serialized resolution result.
  Cannot find selected component (4630) for constraint
  platform-runtime -> org.jetbrains.kotlin:kotlin-stdlib-jdk7:1.8.0
```

Coil 3 是 KMP 库，它的 `-jvm` 变体会多带一个 `platform-runtime` 约束，
和本项目被三条约束锁死的构建链（AGP 8.13.2 / Kotlin 2.2.21 / Gradle 8.14.5）合不来，
报错出现在 `processDebugResources`，看上去跟图片毫无关系，很难排查。

自研版做了四件事，够用且不欠债：

| 能力 | 做法 |
|---|---|
| 内存缓存 | `LruCache`，取堆内存的 1/8，上下限 4 MB ~ 48 MB |
| 磁盘缓存 | OkHttp `Cache` 24 MB —— 后端 StaticFiles 会发 `etag`，二次打开走 304 |
| 降采样 | 先读图片头拿原始尺寸，再算 2 的幂 `inSampleSize`（4000×3000 从 48 MB 降到 2.3 MB） |
| 在途合并 | 同一张图被多张卡片同时请求时只下载一次 |

内存里的图用 `RGB_565` 而非 `ARGB_8888` —— 菜品照和头像都是不透明照片，
没有透明通道，省一半内存，肉眼看不出差别。

加载失败（断网 / 404 / 内存不足）统一返回 `null` 退回占位图，
**不弹任何错误提示** —— 图片加载失败不该干扰用户的主流程。

### 关于图片生成

规则表里一共需要 **31 张图**，现在已生成 **12 张**（见下表），
剩下的 19 张等确认画风后再补。

已生成的 12 张按「覆盖率」挑的，不是随便挑的：

| key | 为什么先做它 |
|---|---|
| `default` | 万能兜底。没有它，任何没命中的菜都是占位图 |
| `tomato-egg-tofu` | MOCK 演示第一道菜（无密钥演示时必出现） |
| `chicken-breast-broccoli` | MOCK 演示第二道菜 |
| `green-pepper-egg` | MOCK 演示第三道菜 |
| `tomato-egg` | 最高频家常菜 |
| `mapo-tofu` | 豆腐类代表 |
| `egg` / `chicken` / `pork` / `tofu` / `greens` / `rice` | 食材兜底，覆盖面最广的六类 |

效果：**12 个真实菜名样本里 8 个命中了专属图**，剩下 4 个落到兜底图。
补完剩余 19 张后，绝大多数家常菜都会有贴合自己的配图。

图片全部放在 `backend/static/recipes/`，**会跟着 Git 提交**
（队友 clone 下来、服务器部署时都会一起带过去）。
原始生成文件（PNG，共 27 MB）留在 `.tmp-images/`，已加进 `.gitignore` ——
保留它只是为了以后想换尺寸/质量时不用重新花积分生成。

### 重新生成或补充图片

```bash
# 1. 把图片按「目录名 = key」放好
#    .tmp-images/tomato-egg/xxx.png

# 2. 转成 JPG 并放到 static/recipes/（会自动报告还缺哪些 key）
"C:/Users/Atao/.workbuddy-ai/binaries/python/envs/default/Scripts/python.exe" \
  tools/import-recipe-images.py

# 3. 验证匹配
cd backend
.venv/Scripts/python.exe scripts/check_images.py
```

转换脚本会把 PNG 压成 JPEG（27.5 MB → 2.4 MB，省 91%），
并把长边缩到 1280 —— 手机在公网加载这几十张图时，这个差别是决定性的。

> ⚠️ **生成图片时一张一张来，不要并行。**
> 并行调用时 `output_dir` 参数会失效，而且输出文件名只带秒级时间戳，
> 同秒完成的多张图会**同名互相覆盖**。
> 本轮就因此丢了 3 张（11 个请求只活下来 8 个），
> 靠「带标签的拼图 + 时间戳」反推归位后才只补生成 3 张。

### 顺带修掉一个规则表顺序 bug

`青椒炒鸡蛋` 原本会被配上**煎鸡腿**的图。

原因：食材规则里鸡肉那条含单字关键词 `鸡`，而 `鸡蛋` 里也含 `鸡`，
按顺序匹配时鸡肉规则先命中。修复是把**蛋类规则提到鸡肉前面**
（`鸡蛋` 先被蛋类命中，而 `鸡肉/鸡胸/鸡腿` 不含 `蛋`，照样落到鸡肉规则），
并给 `青椒炒鸡蛋` 等菜名补了专属规则 + 写了回归测试。

## 追加修复（2026-09-25）：菜谱页同一道菜重复出现

> 原话：「在菜谱页，相同的菜品会重复出现」

### 现象

菜谱页里同一道菜出现很多次。查库确认：该用户 66 条菜谱里只有 37 道不同的菜 ——
「番茄鸡蛋豆腐」重复 **11 次**，「青椒炒鸡蛋」11 次，「香煎鸡胸配西兰花」10 次。

### 根因

`POST /recipes/generate` 落库时是**无条件 INSERT**。
用户每点一次「生成新菜谱」就多存一组，而 MOCK 模式（没配 API Key 时）
和低温度下的模型又总给同样的几道菜，于是同名行越攒越多。

这不是客户端显示问题 —— 数据是真的重复了 11 行。
所以**只在前端去重是不够的**：用户删掉最上面那条，下面那条会立刻顶上来。

### 修法（三层）

1. **落库改成 upsert**（根因）
   `api/v1/recipes.py::_persist_or_update` —— 按「用户 + 菜名」查重，
   已有就更新内容并刷新 `created_at`（让它回到列表最前），没有才新建。
   去重键用**菜名**而不是食材组合：同一道菜重做时用量会变，
   但用户心里的「番茄鸡蛋豆腐」始终是一道菜。

2. **列表查询按菜名只取最新一条**（兜底）
   `list_recipes` 用 `GROUP BY name` 取 `MAX(id)` 子查询，
   即使库里还残留历史重复行，界面也不会出现重复卡片。

3. **单次生成内部去重**
   `recipe_service.generate_recipes` 用 `seen_names` 过滤 ——
   模型偶尔会把同一道菜换个说法给两遍，不去掉的话刚生成就出现两张一样的卡片。

### 清理历史脏数据

代码修好只是止血，库里已有的 29 行重复还在，需要跑一次：

```bash
cd backend
.venv/Scripts/python.exe ../tools/dedupe-recipes.py --dry-run   # 先看要删什么
.venv/Scripts/python.exe ../tools/dedupe-recipes.py             # 真删
```

按「用户 + 菜名」分组，每组保留 `MAX(id)`，同时清掉关联的
`recipe_ingredients` 与 `meal_history` 子行。实测：`recipes` 66 → 37 条。

### 验证

- 端到端测试新增 8 项（`=== 6c. 菜谱去重（回归） ===`），总数 **188 → 196 项全过**。
  其中一条是**反向验证**：删掉一道菜后重新生成必须能回来，
  防止「去重」被写成「这道菜以后永远不再生成」。
- `tools/verify-recipe-dedupe.py` 打**真实库**跑一遍完整流程，
  确认「反复生成后列表不增长 + 库里无同名行」。
